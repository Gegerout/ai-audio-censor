# Проверка наблюдаемости конвейера

Команды рассчитаны на локальный стенд с портами из `.env.example`. Для проверки с нуля используйте отдельное имя проекта, например `export COMPOSE_PROJECT_NAME=audio-observe-demo`, в каждом терминале. Порты должны быть свободны. `down -v` удаляет базы, модели и телеметрию выбранного проекта.

Обычный `docker compose up -d --wait` запускает приложение. Для одного сигнала добавьте профиль перед `up`. На чистом стенде `--profile logs` добавляет Alloy и Loki, `--profile traces` — Collector трейсов и Tempo, `--profile metrics` — Collector метрик и Prometheus. Профиль `observability` объединяет их и добавляет Grafana.

## Чистый запуск и нагрузка

1. Выполните `docker compose --profile '*' down -v`, затем `docker compose --profile observability up -d --build --wait`. На пустом томе `model-init` восстанавливает модель. Войдите в Grafana как `admin` с паролем из `GRAFANA_PASSWORD`. В **Dashboards → AI Audio Censor → Конвейер** появятся 11 панелей. В **Alerting → Alert rules** откройте группу **pipeline**. У обоих правил после первых измерений должно быть состояние **Normal**.
2. Запустите источник с уникальным именем пачки. В первом терминале выполните `run=demo-$(date +%s)`, затем `make source COUNT=6000 RUN="$run"`. Имя сохраняется в атрибуте трейса `batch.name`. Последняя запись `source finished` показывает число подтверждённых публикаций, отказов и пропусков.
3. Откройте графики «Очередь задач и лимит» и «Скорость источника и воркеров». С одним воркером глубина подходит к линии лимита, источник замедляется. После минуты устойчивого заполнения выше 90% проверьте **Firing**. В отдельном терминале выполните `make worker WORKERS=2`. Дождитесь полной минуты с двумя потребителями. Сравните общую скорость и линии отдельных реплик.
4. Во время публикации снимите расход памяти семи сервисов наблюдаемости.

```bash
docker stats --no-stream $(docker compose --profile observability ps -q \
  grafana prometheus metrics-collector otel-collector tempo loki alloy)
```

При проверке с лимитом 100 все 6000 идентификаторов строк нашлись в Postgres со статусом `done` и одной попыткой. Источник получил 1755 отказов и повторил публикации. В 30-секундных окнах источник и воркер показали 18,45 и 19,14 задачи/с. После подключения второй реплики источник показал 38,39, а воркеры вместе — 38,62 задачи/с. Снимок памяти под нагрузкой:

| Сервис | Занято, МиБ | Лимит, МиБ |
| --- | ---: | ---: |
| Loki | 72,63 | 256 |
| Alloy | 57,26 | 144 |
| Collector трейсов | 30,17 | 96 |
| Tempo | 68,55 | 240 |
| Collector метрик | 23,31 | 96 |
| Prometheus | 33,22 | 240 |
| Grafana | 99,28 | 384 |
| **Всего** | **384,42** | **1456** |

## Как проследить задачу

Выполните команду в проекте стенда, чтобы взять идентификатор завершённой задачи.

```bash
docker compose exec -T db sh -c \
  'exec psql -At -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT id FROM tasks WHERE status = 'done' ORDER BY random() LIMIT 1;
SQL
```

В **Explore → Loki** выполните `{service=~"api|source|worker"} |= "TASK_ID"` с полученным идентификатором. В записи `task done` нажмите **Открыть трейс**. Для строки файла родитель называется `source task`, для запроса — `POST /api/v1/tasks`. У `process` посмотрите атрибут `queue.wait.seconds`, затем длительность вложенных `inference` и `database write`. В одном проверочном HTTP-трейсе ожидание составило 10,3 мс, а inference занял 208 мс. **Logs for this span** возвращает к записям данного трейса.

Чтобы найти пачку в **Explore → Tempo**, введите TraceQL `{ span.batch.name = "ИМЯ_ЗАПУСКА" }`. Поиск возвращает подходящие трейсы с учётом лимита выдачи. Полноту пачки проверяют по итогу источника и строкам БД. Для поиска трейсов реплики используйте `{ resource.service.instance.id = "ID_ВОРКЕРА" }`, скопировав значение из переменной **Воркер** на дашборде.

## Ошибки и остановки

| Сценарий | Действие и ожидаемый результат |
| --- | --- |
| HTTP 503 | Во время публикации остановите воркеры командой `docker compose stop worker` и дождитесь заполнения очереди. Отправьте `curl -i -H 'Content-Type: application/json' -d '{"text":"example"}' http://127.0.0.1:8000/api/v1/tasks`. Проверьте 503, `Retry-After`, панель доли 503 и запись `task rejected`. Из неё открывается трейс отказа. Верните воркеры командой `make worker WORKERS=2`. |
| SIGTERM под нагрузкой | При непустой очереди выполните `docker compose stop worker`. В Loki проверьте `{service="worker"} \|~ "worker stopping\|worker stopped"`. Для принятых задач найдите `task done`, спан записи в БД и статус `done`. После запуска оставшиеся сообщения разбираются. |
| Отказ телеметрии | Выполните `docker compose --profile observability stop otel-collector metrics-collector loki`. Создайте задачу через HTTP и запросите URL из заголовка `Location` до получения `done`. Включите сервисы через `docker compose --profile observability up -d --wait otel-collector metrics-collector loki` и отправьте ещё одну задачу. У новой задачи снова появится трейс. Долгоживущий процесс продолжает вести накопительные счётчики. Очереди и повторы экспорта ограничены, поэтому за время сбоя возможны пробелы в логах и трейсах. |

При проверке SIGTERM четыре задачи успели записать результат между событиями `worker stopping` и `worker stopped`. Во время остановки обоих Collector и Loki три новые HTTP-задачи дошли до `done`. После включения сервисов для следующей задачи снова нашёлся полный трейс.

**Сообщение с неверным форматом.** На работающем стенде опубликуйте одну тестовую строку через существующий обменник. В Loki найдите запись `malformed task moved to dead letter queue` по указанному `correlation_id`. Будут видны номер попытки, событие `dlq` и трейс. Формат тела при повторной доставке останется прежним, поэтому попытка одна. На дашборде глубина DLQ вырастет, а правило после двух проверок перейдёт в **Firing**.

```bash
task_id=$(uuidgen)
echo "$task_id"
docker compose exec -T -e DEMO_TASK_ID="$task_id" app python - <<'PY'
import asyncio
import os
from src.broker import TASKS_EXCHANGE, TASKS_ROUTING_KEY, make_broker
from src.config import get_settings

async def main():
    task_id = os.environ["DEMO_TASK_ID"]
    async with make_broker(get_settings()) as broker:
        await broker.publish(b"invalid json", exchange=TASKS_EXCHANGE,
                             routing_key=TASKS_ROUTING_KEY, correlation_id=task_id)

asyncio.run(main())
PY
```

В Management UI RabbitMQ откройте **Queues and Streams → tasks.dlq → Get messages**. В отдельном демонстрационном проекте с одним тестовым сообщением выберите подтверждение без возврата и получите одно сообщение. Глубина опустится до нуля, правило вернётся в **Normal**.

**Ошибка модели с повторными доставками.** Для этого сценария нужна корректная задача и модель, которая стабильно падает на её тексте. На пустой рабочей очереди отдельного стенда остановите штатные воркеры и запустите временный экземпляр. Он использует тот же обработчик, модель из MLflow и настройки телеметрии. Сбой включён для одного тестового текста только в этом процессе.

```bash
docker compose stop worker
demo_worker=$(docker compose run -d --rm --no-deps worker python -c '
import uvicorn
from src.services.inference import InferenceService
from src.worker import app

predict = InferenceService.process
def fail_one(self, text):
    if text == "controlled model failure":
        raise RuntimeError("controlled model failure")
    return predict(self, text)

InferenceService.process = fail_one
uvicorn.run(app, host="0.0.0.0", port=8000, log_config=None)
')
curl -fsS -H 'Content-Type: application/json' -d '{"text":"controlled model failure"}' \
  http://127.0.0.1:8000/api/v1/tasks
```

По `task_id` дождитесь статуса `failed`. При стандартном `TASK_MAX_DELIVERIES=3` в одном трейсе будут три спана `process` со статусом `ERROR`: попытки 1 и 2 содержат событие `requeue`, попытка 3 — `dlq`. В Loki найдутся три записи `inference failed` со стектрейсами. После проверки выполните `docker stop "$demo_worker"` и `make worker WORKERS=1`.

## Вопросы по наблюдаемости

- **Мониторинг и наблюдаемость.** Правило отвечает на заранее заданный вопрос о заполнении очереди. Для расследования неизвестной задержки нужны метрики, события и путь конкретной задачи через сервисы. При заданном наборе рядов стоимость метрик зависит главным образом от частоты сбора, логов — от числа и размера записей, трейсов — от числа отобранных запросов и спанов.
- **Pull и push.** При pull неудавшийся опрос RabbitMQ виден в `up`. При push молчание может означать сбой или штатное завершение процесса. Короткий источник делает финальный экспорт при штатном выходе. Проверить завершение помогают его итоговая запись и состояние задач.
- **Кардинальность.** Каждая комбинация меток образует отдельный ряд Prometheus или поток Loki. Один `task_id` на строку файла дал бы 6000 комбинаций уже у одной метрики. В Loki поле остаётся в JSON. В VictoriaLogs поля записей хранятся отдельно от набора полей потока, а в Elasticsearch для ID можно задать индексируемое поле `keyword`. Стоимость записи и поиска зависит от схемы и диапазона времени. [VictoriaLogs](https://docs.victoriametrics.com/victorialogs/keyconcepts/) · [Elasticsearch](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/keyword)
- **Контекст трейса.** Формат `traceparent` версии 00 — `version-trace_id-parent_id-flags`. Публикатор записывает текущий контекст в AMQP, воркер восстанавливает его до создания `process`. `copy_context().run` переносит его в поток inference. Parent задаёт непосредственного родителя, link указывает дополнительную связь, например с несколькими входными сообщениями. [W3C Trace Context](https://www.w3.org/TR/trace-context/)
- **Семплирование.** Head sampling выбирает трейс в начале, когда исход ещё неизвестен. Tail sampling буферизует спаны и выбирает по результату, например по ошибке или большой задержке. Для сохранения всех ошибок все потенциально интересные спаны должны сначала дойти до точки отбора. На стенде включён `parentbased_always_on`. [OpenTelemetry](https://opentelemetry.io/docs/concepts/sampling/)
- **Collector.** Сервисы отправляют OTLP на одну точку для каждого сигнала. Collector меняет направление экспорта и группирует данные. `memory_limiter` стоит перед `batch`, чтобы ограничить приём до роста пакетов. При исчерпании буферов или времени повторов часть телеметрии теряется.
- **Counter, gauge и histogram.** Счётчик публикаций растёт до рестарта, глубина очереди может падать, гистограмма считает наблюдения по бакетам. Для общего p95 складывают скорости бакетов по `le`, затем вызывают `histogram_quantile`. Среднее двух p95 не учитывает размеры и формы распределений. Точность оценки ограничена шириной бакета. [Prometheus](https://prometheus.io/docs/practices/histograms/)
- **SLO и бюджет ошибок.** Для цели «99% успешно завершённых задач за 6 секунд» разделите прирост бакета `le="6"` на прирост `_count` за то же окно. При 6000 завершениях бюджет равен 60 медленным задачам. Если договорённость охватывает все принятые задачи, в знаменатель нужно включить также проваленные и договориться о сроке для незавершённых. [Реализация SLO](https://sre.google/workbook/implementing-slos/)
- **Алерты.** `for` требует непрерывного нарушения. Краткий пик сбрасывает таймер при следующей нормальной оценке. Для пользователя важны отказы и задержки. Заполнение очереди служит ранним признаком будущих отказов, а попадание в DLQ уже означает необработанную задачу.
- **Хранилища логов.** Loki индексирует метки потока и просматривает отобранные чанки. VictoriaLogs поддерживает фильтры по полям и словам, Elasticsearch строит инвертированные индексы для настроенных полей. При 1 ТБ/день и расследованиях, начинающихся с сервиса и времени, я бы начал с Loki и объектного хранилища. При частом поиске произвольного ID за недели сравнил бы задержку таких запросов и цену индекса на реальной выборке.
- **Противодавление телеметрии.** Во время сбоя экспортёры накапливают только ограниченный объём. Пакетная отправка вынесена из обработки запроса. Для оценки потерь полезно сопоставлять ошибки экспорта, пропуски точек и итоговые строки БД.
- **Sentry.** Событие описывает один сбой. Sentry группирует сходные события в issue, где видны частота, затронутые релизы, ответственный и состояние разбора. Строка лога остаётся записью конкретного запуска. [Термины Sentry](https://docs.sentry.io/concepts/key-terms/)

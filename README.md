# AI Audio Censor

[![CI/CD](https://github.com/Gegerout/ai-audio-censor/actions/workflows/cd.yml/badge.svg)](https://github.com/Gegerout/ai-audio-censor/actions/workflows/cd.yml)

Система автоматического поиска и запикивания нецензурной лексики в аудио. Сейчас в ней есть асинхронный сервис на FastAPI и Postgres с проверками живости и зависимостей, версией приложения и структурированными логами, эксперименты и реестр моделей в MLflow, приём задач через HTTP, очередь задач в RabbitMQ, пакетный источник задач и воркер на FastStream, тесты, Docker и CI/CD с публикацией образа в GitHub Container Registry.

**Стек.** Python 3.11, FastAPI, uvicorn, FastStream, RabbitMQ, asyncpg, pydantic-settings. Окружение и зависимости через uv, линтер и форматтер ruff, тесты pytest с coverage, pre-commit, Docker и docker compose, GitHub Actions, образы в GHCR.

## Эндпоинты

| Метод и путь | Что делает | Коды ответа |
|---|---|---|
| `GET /healthz` | проверяет, что процесс жив, в БД не ходит | 200 |
| `GET /api/v1/version` | версия приложения из `pyproject.toml` | 200 |
| `GET /api/v1/health` | состояние и время ответа Postgres и RabbitMQ | 200 или 503 |
| `POST /api/v1/tasks` | ставит текст в очередь на поиск токсичных фрагментов | 202, 422 или 503 |
| `GET /api/v1/tasks/{task_id}` | состояние задачи, найденные фрагменты и версия модели | 200, 404, 422 или 503 |

`/healthz` нужен Docker и оркестраторам. Это служебный эндпоинт инфраструктуры, а не часть версионируемого API, поэтому он живёт вне `/api/v1` и не изменится с выходом v2.

Версия приложения записана в одном месте, в `pyproject.toml`. Из него её берут `/api/v1/version` и Swagger, а CD при релизе сверяет с ней git тег. Поэтому тег образа и ответ API всегда совпадают.

Ответ `/api/v1/health`, когда Postgres и RabbitMQ работают.

```json
{"status": "ok", "components": {"postgres": {"status": "ok", "version": "17.11", "latency_ms": 1.24, "error": null}, "rabbitmq": {"status": "ok", "version": null, "latency_ms": 0.06, "error": null}}}
```

Если Postgres недоступен, приходит код 503, статус `fail` и имя ошибки, например `ConnectionRefusedError`. Если нет связи с брокером, у `rabbitmq` будет `fail` и `ConnectionError`. Обе проверки ограничены таймаутом `HEALTH_TIMEOUT`, поэтому зависшая зависимость не держит запрос. Swagger открывается на http://localhost:8000/docs.

## Запуск в Docker

Нужны Docker, uv и make. При первом запуске создайте `.env` из шаблона
и задайте пароли обеих баз и RabbitMQ вместо `change-me`. Существующий `.env` заменять не нужно.
До запуска приложения в MLflow должна быть зарегистрирована модель с alias `champion`.

```bash
cp .env.example .env
make install
make mlflow
make eda
make train
make register
make up
curl localhost:8000/api/v1/health
```

`make up` сначала поднимает RabbitMQ и задаёт лимит очереди задач, затем собирает образы
и запускает приложение, воркер, MLflow и обе базы и ждёт их готовности.
Модель загружает воркер до начала обработки задач. Если сервер или alias недоступны,
воркер не стартует. Приложение без брокера не стартует, а без базы стартует и отвечает 503.
После первого развёртывания достаточно `make up`:
данные и реестр сохраняются в Docker volumes и переживают `make down`.

Готовый образ можно скачать из реестра без сборки.

```bash
docker pull ghcr.io/gegerout/ai-audio-censor:latest
```

## MLflow

Для экспериментов и реестра моделей используется MLflow 3.17.1.
Добавьте переменные MLFLOW из `.env.example` в свой `.env` и задайте пароль базы MLflow.
Существующий `.env` целиком заменять не нужно.

```bash
make mlflow
```

UI открывается на http://localhost:5001. Порт можно поменять через `MLFLOW_PORT`.
Для клиента на компьютере адрес сервера `http://localhost:5001`, внутри сети compose
адрес `http://mlflow:5000`.

| Компонент | Назначение | Хранение |
|---|---|---|
| `mlflow` | Tracking Server, UI и Model Registry | обращается к двум хранилищам |
| `mlflow-db` | Backend Store, параметры, метрики, связи с датасетами и версии моделей | PostgreSQL в volume `mlflow-pgdata` |
| Artifact Store | файлы моделей, графики и отчёты | отдельный volume `mlflow-artifacts` |

Сервер принимает и отдаёт артефакты через HTTP. Клиенты используют адрес MLflow
и не монтируют его volume. Поэтому артефакты доступны и с компьютера, и из контейнеров.
В метаданных эксперимента хранится адрес вида `mlflow-artifacts:/...`.

Backend Store и Artifact Store разделены. В базе лежат описания и ссылки,
а содержимое файлов лежит в отдельном хранилище. Для локальной лабораторной
используется файловое хранилище в Docker volume. При переносе на несколько серверов
его можно заменить на S3 через настройку `--artifacts-destination`.

`make mlflow-logs` показывает логи сервера. `make down` останавливает стенд,
а эксперименты и артефакты сохраняются в volumes. Команда `docker compose down -v`
удаляет volumes вместе с данными, для обычной остановки её использовать не нужно.

Зависимости сервера вынесены в группу `tracking`, их версии закреплены в `uv.lock`.
Образ приложения устанавливает группу `web`, которая также содержит зависимости для inference.
Код и параметры обученной модели загружаются из MLflow, папка `ml` в образ не копируется.

### Датасет и EDA

Для экспериментов используется [Toxic Spans](https://huggingface.co/datasets/heegyu/toxic-spans).
В нём английские комментарии и позиции символов, задающие выделенные аннотаторами фрагменты.
Это разметка токсичных фрагментов, включая оскорбления и ненормативную лексику.
Пустой список позиций не означает, что текст нейтрален.
[Инструкция авторов](https://github.com/ipavlopoulos/toxic_spans/blob/master/ACL2022/README.md)
допускает пустую разметку и для сообщений, токсичность которых нельзя локализовать.

Исходные файлы закреплены по ревизии `9062568da9c6383c09193f3aa1f3c48dca925c5f`.
Скрипт проверяет SHA256 обоих CSV, наличие текста и допустимость позиций символов.
Ранее скачанные файлы использует повторно после проверки контрольной суммы.

```bash
make mlflow
make eda
```

`make eda` устанавливает группу `ml` по lock файлу и создаёт запуск `eda`
в эксперименте `toxic-spans`. Сервер должен быть запущен заранее.
Адрес берётся из `MLFLOW_TRACKING_URI`, а если он не задан,
используется localhost и `MLFLOW_PORT` из `.env`, по умолчанию 5001.
Параметры запуска можно задать явно.

```bash
uv run --locked --group ml python -m ml.eda --tracking-uri http://localhost:5001 --experiment toxic-spans
```

В UI откройте Model training, затем Experiments, toxic-spans и запуск eda.
У запуска связаны три датасета, исходный train, подготовленный train и test.
Test используется только для проверки целостности и пересечений, графики построены по train.

| Артефакты запуска | Содержимое |
|---|---|
| `data/raw` | исходные CSV |
| `data/prepared` | снимки текстов и разметки с номерами исходных строк |
| `data/manifest.json` | источники, ревизия, хеши и преобразования |
| `eda/report.md` | результаты анализа и выводы для будущего обучения |
| `eda/audit.json` | размеры выборок, повторы и пересечения |
| `eda/*.png` | длины текстов, доля разметки, баланс слов и частые размеченные слова |
| `eda/train_statistics.csv` | статистики отдельных обучающих текстов |
| `code` | снимок кода анализа и зависимостей |

Локальные копии результатов лежат в `reports/eda/<run_id>`, исходные данные в
`data/raw/<revision>`. Эти папки исключены из Git, результаты сохраняются в MLflow.
Каждый повторный запуск создаёт отдельный Run, а одинаковые данные имеют одинаковый digest.

### Source, digest и lineage

`source` указывает на конкретный CSV в закреплённой версии репозитория.
Для подготовленного датасета это исходный файл до преобразований.

`digest` идентифицирует таблицу текста и разметки. Здесь явно передаются первые
32 символа SHA256 полного JSON представления этой таблицы, включая порядок строк.
Полные SHA256 таблиц, исходных файлов и снимков сохранены в manifest.
Номер строки нужен для проверки происхождения и не входит в схему признаков MLflow.
Позиции в снимке представлены списком, а в таблице MLflow сериализованы в JSON строку.

`lineage` описывает происхождение подготовленных данных.
В manifest записаны родительский и дочерний digest и последовательность преобразований.
Связь с запуском создаётся через `mlflow.log_input`, одного сохранения CSV для этого недостаточно.
MLflow хранит метаданные датасета, поэтому сами файлы дополнительно записываются как артефакты.

Из 10006 строк исходного train исключены 25 строк.
После свёртки регистра и пробелов найдены 11 групп повторов, всего 22 строки.
С test пересекаются 4 разных текста, которым соответствуют 5 строк train.
Категории пересекаются, поэтому числа удалений не складываются напрямую.
Все строки повторяющихся групп исключаются, чтобы не выбирать произвольную разметку.
Остаётся 9981 строка train и 1000 строк test.

Нормализация применяется только для сравнения. Тексты и позиции символов сохраняются,
поэтому разметка остаётся привязана к исходному тексту.
У 48.8 процента подготовленных записей train нет выделенных позиций.
В 1.8 процента слов хотя бы часть слова входит в выделенный токсичный фрагмент.
Из за дисбаланса для будущего сравнения моделей выбрана F1 по символам,
дополнительно будут измеряться precision и recall.

### Обучение и сравнение моделей

```bash
make mlflow
make train
```

`make train` создаёт три запуска в эксперименте `toxic-spans`.
Все они используют одинаковое разделение подготовленных данных: 7984 текста для обучения
и 1997 для валидации. Начальное значение генератора случайных чисел равно 42.
При разделении сохраняется доля текстов с непустой разметкой.
Тестовая выборка используется только для проверки пересечений при подготовке данных.
Для обучения, сравнения моделей и подбора параметров она не используется.

| Запуск | Модель и признаки |
| --- | --- |
| `dictionary` | словарь слов, встретившихся хотя бы дважды и не менее чем в половине случаев отмеченных в обучающей разметке |
| `word_logreg` | логистическая регрессия с признаком самого слова |
| `context_logreg` | та же регрессия с соседними словами, началами и окончаниями слов длиной от двух до четырёх символов |

Словари и признаки строятся только по обучающей части.
Регистр слов приводится к нижнему для признаков, исходные тексты не меняются.
Слово считается положительным примером, если хотя бы часть слова входит в выделенный фрагмент.
На выходе модель возвращает позиции всех символов выбранных слов в исходном тексте.
Пробелы и пунктуация не выделяются, поэтому предсказания могут отличаться от ручных границ.

В регрессиях используются `C=1.0`, `class_weight=balanced`, `solver=lbfgs` и `max_iter=500`.
Одинаковый порог 0.5 применяется к вероятности класса в обеих регрессиях.
У baseline порог 0.5 применяется к доле размеченных вхождений слова в обучающей части.
Параметры выбраны до сравнения и записаны в Runs.

Основная метрика `val_f1` — средняя F1 по текстам, рассчитанная по совпадению позиций.
`val_precision` и `val_recall` также усредняются по текстам.
Если разметка и предсказание пустые, все три оценки равны 1.
Если пуста только одна сторона, все три оценки равны 0.
Для непустых множеств precision равна доле верных позиций среди предсказанных,
recall — доле найденных позиций среди размеченных, F1 — их гармоническому среднему.

Дополнительная метрика `val_f1_annotated` считается только по текстам с непустой разметкой.
Она помогает увидеть качество выделения фрагментов отдельно от совпадений пустых ответов.
`val_f1_micro` считается по суммарным совпадениям и ошибкам во всей валидационной выборке,
поэтому длинные фрагменты влияют на неё сильнее.

В MLflow откройте эксперимент `toxic-spans`, отфильтруйте `tags.stage = 'training'`
и выберите три запуска с одинаковым `batch_id`. Нажмите Compare и сравните
`val_f1`, `val_precision`, `val_recall` и `val_f1_annotated`.
Лучший запуск в этой группе отмечен тегом `best_in_batch=true`.
Общая таблица и выводы сохраняются в каждом из трёх запусков.

| Артефакт | Содержимое |
| --- | --- |
| `data/manifest.json` | источники, размеры, хеши выборок и связь с подготовленным датасетом |
| `data/*.jsonl` | снимки подготовленных данных, обучающей и валидационной частей |
| `validation/predictions.jsonl` | тексты, исходные и предсказанные позиции, оценки отдельных текстов |
| `validation/errors.json` | двадцать примеров с наименьшей F1 среди ошибок |
| `validation/confusion_matrix.png` | матрица ошибок по позициям, проценты рассчитаны внутри строк |
| `validation/f1_distribution.png` | распределение F1 по текстам |
| `comparison/comparison.csv` | метрики, идентификаторы запусков и адреса сохранённых моделей |
| `comparison/report.md` | сравнение моделей и ограничения оценки |
| `code` | снимок кода и зависимостей |

У каждого Run связаны датасеты `train_fit` и `validation` с контекстами `training`
и `validation`. Их digest одинаковы у всех трёх моделей в одной группе запусков.
В manifest записана связь этих выборок с `train_prepared` из EDA.

Каждая модель сохранена в формате MLflow `pyfunc` с кодом, зависимостями и схемой:
вход — таблица с колонкой `text`, выход — таблица с колонкой `positions`, содержащей списки позиций.
После сохранения скрипт загружает модель обратно и сравнивает предсказания на примерах.
Успешная проверка отмечается тегом `model_reload_verified=true`.
Модели доступны в разделе Models соответствующего Run.
Регистрация версий выполняется отдельной командой после сравнения.

Результаты также лежат в `reports/training/<batch_id>`, эта папка исключена из Git.
Повторный `make train` создаёт новую группу запусков. Чтобы задать другую конфигурацию запуска:

```bash
uv run --locked --group ml python -m ml.train --seed 42 --tracking-uri http://localhost:5001
```

Тесты работают на небольших искусственных примерах и не требуют сети или сервера MLflow.
`make test` устанавливает группу `ml`, она также включена в job тестов CI.
Покрытие считается для приложения, подготовки данных, моделей и расчёта метрик.
Скрипты EDA и обучения проверяются полными запусками с чтением артефактов из MLflow.
### Model Registry и итоговая оценка

```bash
make register
```

Команда находит последнюю группу обучения и проверяет, что в ней завершены все три запуска,
у них одинаковые обучающая и валидационная выборки, а сохранённые модели успешно загружались.
Если последняя группа ещё не завершена, команда сообщит об ошибке.
Для выбора конкретной группы передайте её `batch_id`:

```bash
uv run --locked --group ml python -m ml.register --batch-id 4b143af409a6
```

Модели регистрируются под общим именем `toxic-spans-detector` в порядке
`dictionary`, `word_logreg`, `context_logreg`. Каждая версия связана с исходным Run
и сохранённой моделью. Теги версии содержат вариант модели, группу сравнения и валидационную F1.
Номер версии показывает порядок регистрации и сам по себе ничего не говорит о качестве.
Повторная регистрация тех же моделей использует существующие версии.

Alias `champion` получает версия с максимальной `val_f1` в выбранной группе.
При равных оценках используется первый вариант в порядке выше.
Выбор делается только по валидации. Затем выбранная модель проверяется на всех
1000 текстах тестовой выборки, без переобучения и изменения порогов.
Каждый вызов `make register` создаёт отдельный Run `test_champion` с тегом `stage=test`.
Повторная оценка служит проверкой воспроизводимости, результаты test не используются для настройки.

У тестового запуска связаны датасет `toxic-spans/test`, точная версия модели и Run обучения.
Метрики `test_f1`, `test_precision`, `test_recall`, `test_f1_annotated` и `test_f1_micro`
считаются по тем же правилам, что валидационные метрики.
В `test` сохраняются отчёт, предсказания, примеры ошибок и диагностические графики,
в `data` — снимок выборки и manifest с контрольными суммами.
У версии модели тег `test_run_id` указывает на последнюю итоговую оценку.
Локальная копия результатов лежит в `reports/registry/<run_id>`.

В MLflow откройте Model registry, затем `toxic-spans-detector`.
В списке видны версии и alias `champion`, а на странице версии — ссылка на исходный Run.
Чтобы переключить alias на существующую версию, например третью:

```bash
uv run --locked --group ml python -m ml.register --version 3
```

Команда сначала проверяет, что версия существует и загружается, затем меняет alias.
Она не обучает модель и не запускает новую оценку на test.
Для возврата к лучшей модели первой группы используйте `--version 1`.
Имя реестровой модели и alias можно задать через `--model-name` и `--alias`.

Адрес рабочей модели — `models:/toxic-spans-detector@champion`.
Alias является изменяемой ссылкой на версию. Уже загруженный объект модели от смены alias
не меняется: новое значение будет использовано при следующей загрузке.
При итоговой оценке alias разрешается один раз, после чего загружается конкретный номер версии.
Так версия в параметрах Run соответствует модели, которая действительно выполнила предсказания.

Проверки реестра используют отдельную временную SQLite базу и не обращаются к рабочему серверу.
Они проверяют полноту группы, одинаковые выборки, повторную регистрацию и переключение alias.
Полная регистрация и итоговая оценка дополнительно проверяются на локальном MLflow.
Подробнее об alias — в [документации MLflow](https://mlflow.org/docs/latest/ml/model-registry/tutorial).

### Inference через очередь задач

Синхронный `POST /process` из второй работы заменён на очередь. Клиент ставит задачу,
а результат забирает по адресу из заголовка `Location`.

```bash
curl -i -X POST http://localhost:8000/api/v1/tasks \
  -H 'Content-Type: application/json' \
  -d '{"text": "What a stupid idea, you clown."}'
curl http://localhost:8000/api/v1/tasks/9fede58c-13f4-42a1-83a0-f809ab7cf931
```

Ответ на запрос результата для словарного baseline первой группы.

```json
{
  "task_id": "9fede58c-13f4-42a1-83a0-f809ab7cf931",
  "status": "done",
  "attempts": 1,
  "spans": [{"start": 7, "end": 13, "text": "stupid"}],
  "model_name": "toxic-spans-detector",
  "model_version": "1",
  "error": null,
  "enqueued_at": "2026-10-22T12:33:18.028447Z",
  "started_at": "2026-10-22T12:33:18.057958Z",
  "finished_at": "2026-10-22T12:33:18.261618Z"
}
```

`start` включается в фрагмент, `end` не включается: `text[start:end]` даёт выделенный текст.
Позиции считаются по символам Unicode, как индексы строк Python, а не по байтам или единицам UTF-16.
Пробелы, регистр и переносы исходного текста сохраняются. Если модель ничего не выделила,
`spans` будет пустым списком. Это не гарантирует, что текст нейтрален.

Принимается непустая строка длиной до 10000 символов. Пустые строки, строки только из пробелов,
слишком длинные значения и неверный тип данных получают ответ 422 и не попадают ни в базу,
ни в очередь. Модель обучалась на английских комментариях, поэтому её качество на другом языке
или типе текста этим экспериментом не подтверждается.

Воркер при старте один раз разрешает alias через Model Registry, сохраняет номер версии
и загружает именно её. Это исключает ситуацию, когда alias успел измениться между получением
метаданных и загрузкой модели. В каждой задаче и в стартовом логе воркера указана фактически
загруженная версия. Недоступность MLflow после старта воркера не мешает inference.

### Переключение модели на защите

Поставьте задачу и посмотрите `model_version` в результате. Для первой группы модель `champion`
соответствует версии 1. Переключите alias на версию 3:

```bash
uv run --locked --group ml python -m ml.register --version 3
```

Задачи к работающему воркеру всё ещё выполняет версия 1. Перезапустите воркер:

```bash
docker compose restart worker
```

Задачи, которые ждали в очереди во время перезапуска, не теряются. Новые результаты покажут
версию 3 и Run обучения регрессии с контекстом. Inference-код при этом не меняется.
Чтобы вернуть baseline:

```bash
uv run --locked --group ml python -m ml.register --version 1
docker compose restart worker
```

### Ограничения горячего обновления

Смена alias не обновляет модель в памяти работающего воркера. Пока воркер перезапускается,
задачи ждут в очереди, но несколько воркеров при разном времени старта могут получить
разные версии. Новая модель также может требовать других зависимостей или иметь несовместимую схему.

Перезагрузка модели прямо внутри работающего процесса требует координации с запросами:
каждый запрос должен завершиться с той моделью, с которой начал работать. Новую модель нужно
полностью загрузить и проверить до переключения, сохранив старую для уже начатых запросов.
На это время может понадобиться память сразу для двух моделей. Python также кэширует
импортированные модули, что важно при смене кода модели.

Для рабочего сервиса лучше один раз выбрать точную версию, запустить новые экземпляры
с совместимым окружением, загрузить и проверить модель, затем постепенно переключать на них трафик.
Старые экземпляры должны закончить начатые запросы. Предыдущую версию нужно сохранить для отката.
Такой подход позволяет отдельно проверить готовность, отслеживать качество и контролировать,
какая версия обрабатывает запросы.

## Очередь задач в RabbitMQ

Задачи между этапами конвейера передаются через RabbitMQ 4.4. Брокер поднимается командой

```bash
make rabbitmq
```

Management UI открывается на http://localhost:15672, логин и пароль берутся из `RABBITMQ_USER`
и `RABBITMQ_PASSWORD` в `.env`. Статистика в нём обновляется раз в секунду, а не раз в пять,
это задано в `docker/rabbitmq/rabbitmq.conf`. Данные брокера лежат в volume `rabbitmq-data`,
а у контейнера постоянное имя узла, поэтому очереди и сообщения переживают его пересоздание.

| Объект | Тип | Назначение |
|---|---|---|
| `tasks` | обменник direct | принимает задачи и по ключу `tasks` передаёт их в очередь задач |
| `tasks` | очередь classic, durable | задачи, которые ждут воркер, её длина ограничена политикой `tasks-limit` |
| `tasks.dlx` | обменник fanout | принимает отклонённые сообщения из очереди задач |
| `tasks.dlq` | очередь classic, durable | недоставленные сообщения, которые нельзя обработать |

Обменники и очереди описаны в одном месте, в `src/broker.py`. Все компоненты объявляют их
с одинаковыми параметрами, поэтому повторное объявление безопасно.

### Почему classic, а не quorum

У quorum очереди есть встроенный счётчик неудачных доставок, но лимит длины она соблюдает
нестрого. По [документации RabbitMQ](https://www.rabbitmq.com/docs/quorum-queues#length-limit)
при отказе в публикации она может превысить лимит на сообщения, которые уже в пути.
Проверка на RabbitMQ 4.4 это подтвердила. Quorum очередь с лимитом 5 приняла 6 сообщений,
а classic очередь ровно 5. Глубина очереди задач не должна выходить за лимит,
поэтому выбрана classic очередь.

### Лимит очереди

Длину очереди задач ограничивает политика `tasks-limit`.

```json
{"pattern": "^tasks$", "apply-to": "queues", "definition": {"max-length": 100, "overflow": "reject-publish"}}
```

Когда в очереди `TASKS_QUEUE_LIMIT` задач, брокер не удаляет старые сообщения, а отказывает
в публикации новым. Публикующий получает отказ через publisher confirms и знает, что задача
не принята.

Лимит задан политикой, а не аргументом очереди. Аргумент нельзя изменить у существующей
очереди, для смены пришлось бы удалить её вместе с сообщениями. Политика меняется на лету.

```bash
make queue-limit LIMIT=50
```

Новый лимит действует сразу. Если лимит снизить ниже текущей глубины, сообщения, которые
уже в очереди, не удаляются, отказ получают только новые публикации. Проверка на работающем
брокере дала такой результат. При лимите 100 из 103 публикаций приняты 100, после снижения
до 50 отказ получили все 5 новых публикаций, после повышения до 120 приняты ещё ровно 20.

Политику записывает разовая задача `rabbitmq-setup` через HTTP API брокера. Она сначала
задаёт лимит, а потом объявляет очереди, поэтому очередь задач не существует без лимита.
`make up` и `make rabbitmq` запускают её сами после того, как брокер готов. HTTP API здесь
нужен только для настройки, сигнал о переполнении компоненты получают от брокера по AMQP.
Загрузить политику из файла definitions при старте брокера не получится без пароля
в репозитории. При такой загрузке RabbitMQ не создаёт пользователя по умолчанию,
и его пришлось бы описать в том же файле.

## Хранилище задач

Задачи и их результаты лежат в таблице `tasks` базы приложения. Её описание и все запросы
к ней находятся в `src/storage.py`.

| Колонка | Что хранит |
|---|---|
| `id` | идентификатор задачи, первичный ключ |
| `text` | текст, который нужно обработать |
| `status` | `pending`, `processing`, `done` или `failed` |
| `attempts` | сколько раз задача доставлялась воркеру |
| `result` | найденные фрагменты в JSON |
| `model_name`, `model_version` | модель, которая выполнила задачу |
| `error` | причина, если задача провалена |
| `enqueued_at`, `started_at`, `finished_at` | время приёма, начала и окончания обработки |

### Идемпотентность

Уникальность задачи обеспечивает первичный ключ `id`, а не проверка в коде. Каждая операция
выполняется одним запросом, поэтому между проверкой и записью нет окна для гонки.

| Операция | Запрос | Что происходит при повторе |
|---|---|---|
| начало попытки | `INSERT ... ON CONFLICT (id) DO UPDATE` увеличивает `attempts` | вторая строка не появляется, у выполненной задачи ничего не меняется |
| сохранение результата | `UPDATE ... WHERE status <> 'done'` | второе сохранение ничего не перезаписывает |
| провал задачи | `UPDATE ... WHERE status <> 'done'` | выполненную задачу провалить нельзя |

Тесты проверяют это на настоящем Postgres в контейнере. Десять одновременных доставок одной
задачи оставляют одну строку и десять учтённых попыток. Из пяти одновременных сохранений
результата срабатывает ровно одно.

Счётчик `attempts` увеличивается при каждой доставке до начала обработки. Поэтому попытка
учитывается, даже если воркер упал посреди обработки и сообщение вернулось в очередь.
По этому счётчику ограничивается число повторных доставок.

### Задачи из API

`create_pending` записывает задачу со статусом `pending` в открытой транзакции. Если брокер
отказал в публикации, транзакцию откатывают и в базе ничего не остаётся. Тест
`test_rolled_back_pending_task_leaves_nothing` это проверяет. Источник задач в базу не пишет,
он связан с воркером только через RabbitMQ. Запись о его задаче создаёт воркер при первой
доставке.

### Создание таблицы

Таблицу создают процессы при старте командой `CREATE TABLE IF NOT EXISTS`. Если несколько
процессов делают это одновременно, Postgres может ответить ошибкой уникальности в системном
каталоге. Проверка на Postgres 17 показала 210 таких ошибок за 30 раундов по 8 процессов.
Поэтому создание выполняется под транзакционной блокировкой `pg_advisory_xact_lock`,
и с ней ошибок не было ни одной.

## Воркер

Воркер это отдельный процесс `src/worker.py` на FastStream. С источником задач и API он связан
только через RabbitMQ, берёт задачи из очереди `tasks`, выполняет inference и пишет результат
в таблицу `tasks`. `make up` запускает его вместе со стендом.

```bash
make worker
make worker-logs
```

При старте воркер один раз разрешает alias `champion` и загружает модель из MLflow, затем
подключается к базе и только после этого начинает брать задачи. Версия модели попадает в лог
`worker started` и в каждую выполненную задачу. Если MLflow или alias недоступны, воркер
не стартует.

Inference выполняется в отдельном пуле из `WORKER_CONCURRENCY` потоков. Длительность одной задачи
задаёт `INFERENCE_SECONDS`. Модель отрабатывает, а остаток времени поток пула ждёт, поэтому замеры
повторяются на любой машине. Цикл событий в это время свободен.

`/healthz` воркера отдаёт FastStream через `make_ping_asgi`, он отвечает 204, если есть связь
с брокером. HTTP запросы и обработчики задач живут в одном цикле событий. Поэтому ответ
на healthcheck во время обработки показывает, что inference цикл не блокирует. Под полной
нагрузкой из 59 запросов к `/healthz` все получили 204, худший ответ пришёл за 5,1 мс.
На этот же адрес смотрит healthcheck из `Dockerfile`.

### prefetch_count

`prefetch_count` равен размеру пула, по умолчанию 4. Брокер отдаёт воркеру не больше
неподтверждённых сообщений, чем у него потоков. Каждое полученное сообщение сразу попадает
в свободный поток.

Один воркер выполняет не больше 4 / 0,2 = 20 задач в секунду. Замер дал 19,1 задачи в секунду.
При лимите очереди 100 задача ждёт в очереди не дольше 100 / 20 = 5 секунд. При заполненной
очереди среднее время от приёма до результата вышло 4,5 секунды.

| prefetch | Что происходит |
|---|---|
| меньше пула | часть потоков простаивает, пропускная способность падает до prefetch / 0,2 задачи в секунду |
| равен пулу | потоки заняты, лишние задачи ждут в очереди брокера, где их видно и где действует лимит |
| больше пула | лишние задачи ждут потока в памяти воркера. Лимит очереди их не считает, второй воркер их не получит, а при падении воркера они вернутся в очередь с потраченной попыткой |

Для экспериментов prefetch задаётся отдельно от пула.

```bash
make worker PREFETCH=10
make worker WORKERS=2
```

Здесь есть ловушка FastStream. Очередь задач объявляет сам подписчик на своём канале
с prefetch. FastStream запоминает объявленные очереди по имени. Если объявить очередь `tasks`
раньше подписчика, он получит её вместе с общим каналом без лимита. Так и вышло в первой версии
воркера. Тогда 300 задач ушли в память воркера за 0,2 секунды, брокер не отказал ни разу,
а время в обработке выросло до 6,8 секунды. Поэтому при старте воркер объявляет только обменник
и очередь недоставленных сообщений. Тест `test_worker_takes_only_prefetch_messages` проверяет
это на настоящем RabbitMQ. С ошибкой воркер забирает 6 задач из 6, без неё 2 из 6.

### Подтверждение сообщений

Выбрана политика `AckPolicy.REJECT_ON_ERROR`. Подтверждение уходит после того, как обработчик
вернул управление, а возвращает он его только после записи результата в базу.
Тест `test_task_result_is_stored_before_ack` проверяет, что в момент ack задача уже `done`.

| Политика | Что делает | Почему подходит или нет |
|---|---|---|
| `ACK_FIRST` | подтверждает до обработки | при падении воркера задача потеряна |
| `ACK` | подтверждает даже при ошибке | задача с ошибкой пропадает без следа |
| `NACK_ON_ERROR` | возвращает сообщение в очередь при любой ошибке | у classic очереди нет счётчика доставок, некорректное сообщение крутится бесконечно |
| `MANUAL` | всё вручную | ack нужен в каждой ветке кода, его легко забыть |
| `REJECT_ON_ERROR` | ack при успехе, reject без возврата при неожиданной ошибке | выбрана, неожиданная ошибка попадает в DLQ, а не в бесконечный повтор |

Повторы задаются явно через `RejectMessage(requeue=True)`. Их число ограничивает счётчик
`attempts` в базе, а не брокер. У classic очереди своего счётчика нет. У quorum очереди он есть,
но в RabbitMQ 4.4 возврат через nack его не увеличивает. Проверка дала 2315 доставок одного
сообщения без остановки. Счётчик в базе увеличивается до начала обработки, поэтому он
учитывает и доставки, на которых воркер упал.

| Ситуация | Что делает воркер | Куда идёт сообщение |
|---|---|---|
| задача выполнена и записана | ack | удаляется из очереди |
| повторная доставка выполненной задачи | ack без второго inference | удаляется из очереди |
| некорректный JSON или поля | reject без возврата | `tasks.dlq` |
| ошибка модели, попытки ещё есть | пауза `TASK_RETRY_DELAY_SECONDS`, reject с возвратом | обратно в `tasks` |
| ошибка модели на последней попытке | статус `failed`, reject без возврата | `tasks.dlq` |
| доставок больше `TASK_MAX_DELIVERIES` | статус `failed` без inference, reject без возврата | `tasks.dlq` |
| база недоступна | пауза, reject с возвратом | обратно в `tasks` |
| неожиданная ошибка в коде | reject без возврата по политике | `tasks.dlq` |

Пауза перед возвратом нужна потому, что брокер сразу отдаёт возвращённое сообщение снова.
Пока идёт пауза, задача занимает место в prefetch, и воркер не берёт новые задачи.
Сбой базы не отправляет задачи в DLQ. Пока база недоступна, попытка не записывается
и не считается.

### Остановка

По SIGTERM uvicorn завершает lifespan, и FastStream перестаёт брать новые сообщения. Начатые
задачи он ждёт до `WORKER_GRACEFUL_TIMEOUT` секунд, по умолчанию 30. Полученные, но не начатые
сообщения остаются неподтверждёнными и возвращаются в очередь при закрытии канала. Затем
воркер дожидается потоков пула и закрывает соединения с базой. В compose `stop_grace_period`
равен 40 секундам. Это больше 30 секунд, поэтому Docker не убивает воркер раньше времени.

| Проверка | Результат |

| 300 задач при лимите очереди 100 | очередь держалась на 100, у воркера 4 неподтверждённых, брокер отказал в публикации 49 раз, все 300 выполнены с первой попытки |
| длительность задачи | в среднем 0,20 секунды, как в `INFERENCE_SECONDS` |
| `/healthz` под нагрузкой | 59 запросов, все 204, худший ответ за 5,1 мс |
| SIGTERM посреди нагрузки | 4 начатые задачи записаны, затем воркер остановился, 94 задачи остались в очереди, после запуска все 150 выполнены по одному разу |
| SIGKILL посреди нагрузки | 4 задачи в работе вернулись в очередь и после запуска выполнены со второй попытки, потерь нет |
| остановка Postgres на 6 секунд | воркер оставался healthy, задачи возвращались в очередь примерно 4 раза в секунду, после возврата базы все 120 выполнены, в DLQ ничего |
| некорректное сообщение | сразу попало в `tasks.dlq` |
| второй воркер | 38 задач в секунду вместо 19 |

Тесты воркера в `tests/test_worker.py` работают на `TestRabbitBroker` и настоящем Postgres.
Брокер в памяти не умеет prefetch и DLQ, поэтому `tests/test_worker_broker.py` проверяет
их на настоящем RabbitMQ в контейнере.

## Источник задач

Источник это отдельный процесс `src/source.py`. Он пакетно отправляет на обработку строки большого
файла и связан с воркером только через RabbitMQ, в базу он не пишет. По умолчанию он читает колонку
`text_of_post` из `train.csv` датасета Toxic Spans, это 10 006 постов. Файл появляется после
`make eda`. Одному воркеру на них нужно больше восьми минут.

```bash
make source RUN=batch1
make source RUN=batch1 START=200 COUNT=100
```

`RUN` задаёт имя запуска. Id задачи вычисляется из имени запуска, имени файла и номера строки,
поэтому повторный запуск с тем же `RUN` не создаёт новых задач. Воркер узнаёт выполненные задачи
по ключу в базе и подтверждает их без inference. `START` и `COUNT` задают диапазон строк.

### Как источник узнаёт о переполнении

Источник публикует каждую задачу с подтверждением брокера и ждёт ответа. Когда в очереди
`TASKS_QUEUE_LIMIT` задач, брокер по политике `reject-publish` отвечает отказом, и публикация
завершается ошибкой `DeliveryError`. Источник выдерживает паузу и повторяет ту же задачу.
Следующую строку файла он читает только после подтверждения. Поэтому в каждый момент он держит
одну задачу, а остальные остаются в файле. Сообщения сохраняются на диск брокера, а сообщение,
которое не попало ни в одну очередь, тоже вызывает ошибку и повторяется, а не теряется молча.

Пауза растёт вдвое после каждого отказа, от `SOURCE_INITIAL_DELAY_SECONDS` до
`SOURCE_MAX_DELAY_SECONDS`, и вдвое сокращается после каждой принятой задачи. Ниже начального
значения она падает до нуля, и источник снова публикует без пауз.

| Параметр | Значение | Откуда |
|---|---|---|
| начальная пауза | 0,05 секунды | за это время воркер освобождает одно место в очереди, 0,2 секунды на задачу и 4 потока |
| предельная пауза | 5 секунд | за это время воркер разбирает полную очередь, 100 задач по 20 в секунду, дольше ждать нет смысла |

Пауза всегда больше нуля, поэтому повторы не превращаются в холостой цикл. Скорость не задана
заранее. Источник публикует ровно с той скоростью, с которой воркеры освобождают очередь,
и сам подстраивается, когда воркеров становится больше или меньше.

Раз в секунду источник пишет в лог `source progress` с числом принятых задач, скоростью за
интервал, числом отказов и текущей паузой. В итоге запуска есть `next_row`, первая строка,
которую брокер ещё не принял. По SIGTERM или Ctrl+C источник сразу прерывает паузу, пишет итог
и завершается, а продолжить можно с `START` равным `next_row`.

### Почему так, а не иначе

| Способ | Почему не выбран |
|---|---|
| фиксированный лимит скорости | не знает, сколько работает воркеров, при одном переполняет очередь, при двух недогружает их, его надо перенастраивать вручную |
| очередь или буфер в памяти источника | давление не доходит до источника, память растёт без предела, при падении источника буфер пропадает |
| опрос глубины очереди через Management API | статистика обновляется раз в секунду, между проверкой и публикацией очередь успевает заполниться, это лишняя нагрузка на HTTP API, который нужен для управления, а не для данных |
| `drop-head` вместо `reject-publish` | брокер молча выбрасывает самые старые задачи |
| блокировка соединений брокером при нехватке памяти или диска | срабатывает на весь узел и всех публикующих сразу, включая API, а не на одну очередь |
| пачка публикаций без ожидания подтверждения каждой | неподтверждённые сообщения надо держать для повтора, это тот же буфер в памяти |

Подтверждения брокера вместе с `reject-publish` дают сигнал сразу в ответ на конкретную публикацию,
точно по одной очереди и без нового компонента.

### Перезапуск брокера

Источник переживает перезапуск RabbitMQ. На время рестарта публикация падает с ошибкой канала,
источник пишет `broker unavailable`, ждёт с растущей паузой и продолжает после переподключения.

У рестарта под нагрузкой есть особенность. Лимит длины classic очереди считает только готовые
сообщения, а неподтверждённые у воркеров в него не входят. Когда соединения закрываются,
неподтверждённые сообщения возвращаются в очередь, и в ней оказывается больше лимита. Живой
брокер их не трогает и просто не принимает новые публикации, пока очередь не опустится ниже
лимита. Проверка это подтвердила. Тестовый потребитель забрал 4 сообщения из полной очереди
и закрыл соединение, в очереди стало 104 сообщения, в DLQ ничего, новые публикации получили отказ.
Поэтому остановка или падение воркера задачи не теряет.

Но при запуске брокер сразу обрезает очередь до лимита. Излишек уходит в `tasks.dlq` с причиной
`maxlen`, это видно в заголовке `x-death`. Те же 104 сообщения после рестарта брокера разделились
на 100 в очереди и 4 в DLQ. Под нагрузкой с двумя воркерами в DLQ так попали 8 задач,
а в базе они остались в статусе `processing`.

Задачи при этом не потеряны, их можно довыполнить повторным запуском той же партии. Источник
отправит те же id, выполненные задачи воркер подтвердит без inference, а оставшиеся выполнит.
Проверка показала именно это. Из 800 задач партии 792 воркер пропустил как повторы, а 8 выполнил
со второй попытки.

## API задач

`POST /api/v1/tasks` принимает текст и отвечает сразу, не дожидаясь обработки. Если задача
принята, приходит 202 с её id и заголовком `Location`, по которому лежит результат. Если принять
её нельзя, приходит 503 с заголовком `Retry-After`. Сам inference выполняет воркер.

### Как задача попадает в очередь

API открывает транзакцию и записывает задачу со статусом `pending`. Затем публикует её
с подтверждением брокера и только после подтверждения фиксирует транзакцию. Если брокер отказал,
исключение откатывает транзакцию, и в базе не остаётся задачи в статусе `pending`. Весь приём
ограничен `TASKS_TIMEOUT_SECONDS`, поэтому запрос не висит, даже если база или брокер зависли.

Воркер может получить сообщение раньше, чем API зафиксирует транзакцию. Тогда его
`INSERT ... ON CONFLICT` ждёт эту транзакцию на первичном ключе и после фиксации переводит
задачу из `pending` в `processing`. Повторной записи не появляется.

База и брокер не входят в одну транзакцию, это задача двойной записи. Выбранный порядок
закрывает главный случай. Отказ брокера не оставляет в базе задачу, которой нет в очереди.
Остаётся узкое окно, когда брокер подтвердил публикацию, а фиксация транзакции упала. Тогда
сообщение есть, а строки API нет. Воркер создаёт строку сам и выполняет задачу, но клиент
получил ошибку и может отправить текст ещё раз. Outbox закрыл бы это окно, но с ним API пишет
только в базу, а публикует отдельный процесс позже. Тогда API не узнал бы сразу, что очередь
заполнена, и не смог бы ответить 503 по сигналу брокера.

### Retry-After

`Retry-After` равен времени, за которое воркеры разберут задачи, которые уже ждут в очереди.

```
Retry-After = ⌈ глубина очереди / (число воркеров × WORKER_CONCURRENCY / INFERENCE_SECONDS) ⌉
```

Задача, принятая раньше, всё равно ждала бы эти задачи. Повтор до этого срока не ускорит
результат, а только добавит нагрузки. Глубину очереди и число воркеров API узнаёт у брокера
повторным объявлением очереди по AMQP, это свежие счётчики, а не статистика Management API,
которая отстаёт на интервал обновления. При полной очереди из 100 задач один воркер даёт
5 секунд, два воркера 3 секунды.

Значение ограничено снизу одной секундой, а сверху `TASKS_RETRY_AFTER_MAX_SECONDS`, 30 секунд.
Верхняя граница нужна, когда оценить время нельзя. Если воркеров нет, очередь не разбирается,
а новый воркер стартует около 20 секунд вместе с загрузкой модели. Ту же границу клиент получает,
если недоступна база или брокер. Скорость одного воркера API берёт из общих настроек, поэтому
при запуске воркеров с другим `CONCURRENCY` оценка смещается пропорционально, а число воркеров
всегда берётся у брокера.

### Почему это load shedding, а не backpressure

Backpressure передаёт сигнал перегрузки назад, тому, кто производит работу, и тот замедляется,
ничего не теряя. Так работает источник. Он наш, он может подождать, а задачи остаются у него
в файле. Клиент API внешний, замедлить его мы не можем. Если держать его запрос, пока не
освободится место, в API копились бы висящие запросы и открытые соединения, а клиенты ловили бы
таймауты. Это тот же неограниченный буфер, только в памяти API.

Поэтому API на границе системы сбрасывает лишнюю нагрузку. Задача сразу не принимается,
ответственность за повтор переходит к клиенту, а `Retry-After` только подсказывает, когда
повторить. Это load shedding. От rate limiting он отличается тем, что срабатывает
по фактической перегрузке, по заполненной очереди, а не по заранее заданной квоте запросов.

### Проверка на работающем стенде

Источник держал очередь заполненной, а в API шли запросы раз в 0,1 секунды.

| Проверка | Результат |
|---|---|
| один воркер, 40 запросов | 25 приняты, 15 получили 503 с `Retry-After: 5`, самый долгий отказ пришёл за 11 мс |
| два воркера, 40 запросов | 26 приняты, 14 получили 503 с `Retry-After: 3` |
| строки в базе | ровно столько, сколько ответов 202, для отказов строк нет |

| `POST /process` | 404, эндпоинт заменён |

`tests/test_tasks_api.py` проверяет API на настоящем Postgres и брокере в памяти.

## Тесты конвейера

Модульные тесты работают на `TestRabbitBroker`, брокере FastStream в памяти. Он не умеет prefetch,
лимит очереди и DLQ, поэтому эти механизмы проверяются на настоящем RabbitMQ 4.4 в контейнере
Testcontainers, той же версии, что в compose. Postgres в тестах тоже настоящий, в контейнере.
Контейнеры поднимаются один раз на прогон, поэтому `make test` нужен запущенный Docker, а CI
запускает те же тесты на GitHub.

| Файл | Брокер | Что проверяет |
|---|---|---|
| `tests/test_worker.py` | в памяти | ack после записи, повторы до лимита и DLQ, идемпотентность, некорректные сообщения, healthcheck во время inference, мягкая остановка |
| `tests/test_source.py` | в памяти | ленивое чтение файла, рост паузы до предела, повтор той же задачи без чтения вперёд, остановка во время паузы |
| `tests/test_tasks_api.py` | в памяти | 202 и `Location`, результат задачи, 503 без строки `pending`, таймаут, формула `Retry-After` |
| `tests/test_worker_broker.py` | настоящий | воркер берёт не больше prefetch, некорректное сообщение и исчерпанные повторы попадают в DLQ |
| `tests/test_source_broker.py` | настоящий | переполнение очереди, источник замедляется до скорости потребителя и не теряет задачи |
| `tests/test_tasks_broker.py` | настоящий | переполнение очереди, API сразу отвечает 503, `Retry-After` зависит от числа воркеров |

Главный тест переполнения `test_source_slows_to_consumer_speed_without_losing_tasks` задаёт
очередь с лимитом 5 и медленного потребителя, который тратит 0,05 секунды на сообщение.
Источник отправляет 30 задач, а отдельная задача каждые 10 мс замеряет глубину очереди.
Тест проверяет, что очередь дошла ровно до лимита и ни разу его не превысила, что брокер
отказывал в публикации, что все 30 задач пришли по одному разу и в порядке строк файла
и с признаком сохранения на диск. Источник при этом не закончил раньше, чем потребитель
освободил место под последние задачи. Второй тест убирает потребителя. Источник заполняет
очередь до лимита и за секунду получает около десяти отказов, а не тысячи, как при холостом цикле.

## Локальная разработка

Нужны uv и Docker. Приложение читает настройки из `.env`, а Postgres и RabbitMQ поднимаются
из того же compose. Воркеру дополнительно нужна зарегистрированная модель в MLflow.

```bash
make install
make db
make rabbitmq
make run
```

| Команда | Что делает |
|---|---|
| `make install` | ставит зависимости строго по `uv.lock` и хуки pre-commit |
| `make lint` | ruff и проверка формата, как в CI |
| `make fmt` | исправляет то, что ruff умеет сам, и форматирует код |
| `make test` | тесты с покрытием, ниже 90 процентов команда падает, нужен запущенный Docker |
| `make check` | lint и test вместе, удобно перед push |
| `make run` | приложение локально с перезапуском при изменении кода, нужны `make db` и `make rabbitmq` |
| `make db` | только Postgres в Docker, доступен на localhost |
| `make up`, `make down` | весь стенд в Docker |
| `make logs` | логи приложения в реальном времени |
| `make mlflow` | сервер MLflow и отдельная база метаданных |
| `make eda` | подготовка датасета и анализ данных |
| `make train` | обучение и сравнение трёх моделей |
| `make register` | регистрация версий, выбор champion и итоговая оценка |
| `make rabbitmq` | RabbitMQ, лимит очереди задач и объявление очередей |
| `make queue-limit LIMIT=50` | новый лимит очереди задач на лету, без потери сообщений |
| `make worker` | пересоздаёт воркеры, `WORKERS`, `PREFETCH` и `CONCURRENCY` задают их число, prefetch и пул |
| `make worker-logs` | логи всех воркеров в реальном времени |
| `make source RUN=batch1` | пакетная отправка строк файла, `START` и `COUNT` задают диапазон |

Хуки pre-commit запускаются на каждый коммит. Они проверяют ruff и формат, пробелы в конце строк, перевод строки в конце файла, синтаксис YAML и TOML, большие файлы и случайно добавленные приватные ключи.

| `TASK_MAX_DELIVERIES` | `3` | сколько раз задача доставляется воркеру, потом уходит в DLQ |
| `TASK_RETRY_DELAY_SECONDS` | `1.0` | пауза перед возвратом задачи в очередь после ошибки |
| `WORKER_GRACEFUL_TIMEOUT` | `30` | сколько секунд воркер ждёт начатые задачи при остановке |
| `SOURCE_INITIAL_DELAY_SECONDS` | `0.05` | первая пауза источника после отказа брокера |
| `SOURCE_MAX_DELAY_SECONDS` | `5.0` | предельная пауза источника |
| `SOURCE_REPORT_SECONDS` | `1.0` | как часто источник пишет скорость публикации в лог |

Если меняется `MLFLOW_PORT`, обновите `MLFLOW_TRACKING_URI` для локального запуска.
Внутри сети compose адрес сервера остаётся прежним.

Без пароля приложение не стартует, а compose останавливается с понятной ошибкой. Значений по умолчанию для секретов нет специально.

## Логи

Каждая строка лога это один JSON объект. Запрос получает `request_id`, он возвращается в заголовке `X-Request-ID`, и все логи одного запроса связаны этим id. Запросы healthcheck к `/healthz` пишутся на уровне DEBUG, чтобы не забивать логи. Логи FastStream идут в том же формате, запись о каждом полученном сообщении видна на уровне DEBUG, а итог задачи воркер пишет сам вместе с `task_id`.

```json
{"ts": "2026-10-01T08:41:48.012921+00:00", "level": "INFO", "logger": "src.app", "request_id": "fb96b9b0cef340be8061f7c732a59da8", "msg": "request handled", "method": "GET", "path": "/api/v1/health", "status": 200, "duration_ms": 24.1}
```

## CI/CD

**CI** в `ci.yml` проверяет линтер, формат, остальные хуки pre-commit и тесты с порогом покрытия 90 процентов. Ошибки ruff появляются аннотациями на строках кода, таблица покрытия выводится в сводке запуска. CI запускается на pull request и на push в любые ветки, кроме `main`.

**CD** в `cd.yml` запускается на push в `main` и на теги релиза. Сначала он прогоняет тот же CI, и только если всё зелёное, собирает образ и публикует его в `ghcr.io/gegerout/ai-audio-censor`.

| Событие | Теги образа |
|---|---|
| push в `main` | `main` и `sha-<коммит>` |
| тег `vX.Y.Z` | `X.Y.Z`, `X.Y`, `latest` и `sha-<коммит>` |
| pull request | ничего не публикуется |

`sha` указывает на конкретный коммит, `main` на последний коммит ветки, а semver теги и `latest` двигаются только при релизе. В образ записываются OCI метки с версией, коммитом и ссылкой на репозиторий.

### Выпуск релиза

```bash
uv version --bump patch
git commit -am "chore: release v0.1.1"
git tag v0.1.1
git push origin main v0.1.1
```

`uv version` меняет версию в `pyproject.toml` и `uv.lock`. Если тег не совпадёт с версией в `pyproject.toml`, CD упадёт до публикации образа.
